# Web 平台测试报告

测试环境：Windows / Python 3.12 / Flask 3.1 / MySQL 8.4.9，数据库 `retail_marketing_codex`（`127.0.0.1:3308`）。

## 数据回归

| 表 | 开发后行数 | 预期 |
|---|---:|---:|
| member | 200,000 | 200,000 |
| sales_order | 600,000 | 600,000 |
| order_item | 2,000,000 | 2,000,000 |
| coupon_instance | 1,493,852 | 1,493,852 |

结果：四张大表数量与开发前一致。只新增了 `user_account`（2 条演示账号），其外键指向既有 `member`；没有修改或删除原有业务数据、约束或索引。

## 自动化测试

- 原 SQL 项目负向约束测试：27 / 27 PASS。
- Web pytest：6 / 6 PASS。
  - 健康检查和未登录跳转；
  - CUSTOMER 禁止访问 ADMIN；
  - 客户以他人订单 ID 请求详情返回 404；
  - ADMIN 核心首页、列表页、性能页响应正常；
  - 管理订单复合筛选（状态、日期、用券、实付区间）和分页参数保留；
  - 商品销量只按已完成订单聚合；
  - 会员优惠券只读取当前会话会员、状态筛选与分页；
  - 图表脚本来自本地静态资源，不依赖 CDN。

## 页面集成检查

`integration_report.json` 记录了顺序执行的 19 个页面/API，全部返回 HTTP 200：健康检查、客户端首页/订单/订单详情/分析/优惠券/资料，以及商家总览、销售、订单、商品、会员、RFM、复购、召回、优惠券、营销、数据质量、性能。

本次最终性能实测见 `performance_benchmark.json`：冷缓存销售分析 50.55 秒、券运营 30.76 秒、数据质量 25.87 秒；预热完成后上述路由均为 0.00–0.01 秒。这些页面确实在百万级表上运行真实 SQL，而不是返回假数据；应用通过 `run.py` 在**同一 Flask 进程**启动预热，适合连续课堂演示，进程重启后会从数据库重新计算。
